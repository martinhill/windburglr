Windburglr
==========

`Windburglr` is a mobile-friendly web application that collects and displays real-time and historical wind data from online weather stations.

This project is a monorepo containing two sub-projects:

-   **`scraper`**: A Python application responsible for scraping wind data from various sources and storing it in a database. For more details, see the [`scraper/README.md`](scraper/README.md).
-   **`webapp`**: A FastAPI web application that provides a web interface for viewing the collected wind data. It features real-time updates via WebSockets and interactive charts. For more details, see the [`webapp/README.md`](webapp/README.md).

## Development environment

A single Nix flake at the repository root provides the toolchain (Python 3.13, uv, PostgreSQL 18 with
the Apache-licensed TimescaleDB build, and Node.js 22 / pyright for the webapp). Each sub-project's
`.envrc` loads its shell (`use flake ..#webapp`, `use flake ..#scraper`); without direnv, run
`nix develop ..#webapp` (or `#scraper`, or `nix develop` at the root).

Loading the environment only sets variables (`PGHOST`, `PGUSER`, `PGDATABASE`, the virtualenv `PATH`);
it never starts anything. That keeps it cheap enough to load on every command, which is what
agent shells and direnv do. The database is managed explicitly with `scripts/db.sh` (or `make db-*`
at the root or in `webapp/`):

```bash
scripts/db.sh up          # start the cluster; build the template and dev database if needed
scripts/db.sh status      # list databases
scripts/db.sh reset-dev   # recreate windburglr_dev from the current schema (destroys its data)
scripts/db.sh down        # stop the cluster
```

There is one socket-only cluster (no TCP port) in `.pgdata/` of the main checkout, shared by both
sub-projects and all git worktrees. It holds:

-   **`windburglr_dev`**: persistent development database with the schema, the `scraper` and `webapp`
    roles from `common/roles.sql`, and `common/initial_data.sql`. Connect the apps as their own role,
    e.g. `postgresql://scraper@/windburglr_dev` and `postgresql://webapp@/windburglr_dev`, to get
    the same least-privilege permissions as production. Schema changes are not applied to it
    automatically; apply them by hand or run `reset-dev`.
-   **`windburglr_template`**: schema and roles only. It is rebuilt automatically whenever
    `common/timescaledb_schema.sql` or `common/roles.sql` changes.
-   **`windburglr_test_*`**: each pytest session clones its own database from the template and drops
    it afterwards, so concurrent runs (in different worktrees, say) don't interfere. Set
    `TEST_DATABASE_URL` to use a specific database instead. `scripts/db.sh test-clean` removes
    databases left behind by aborted runs.

## Database

This project uses [PostgreSQL](https://www.postgresql.org/) with the [TimescaleDB](https://www.timescale.com/) extension for storing and querying time-series wind data. TimescaleDB is used to efficiently handle the large volume of time-series data generated by the scraper.

### Initialization

To initialize the database, you can use the SQL files provided in the `common/` directory. These files should be run in the following order:

1.  **`timescaledb_schema.sql`**: This file creates the database schema, including the `station` and `wind_obs` tables. It also creates a hypertable for the `wind_obs` table if the TimescaleDB extension is available.
2.  **`initial_data.sql`**: (Optional) This file inserts the initial data into the `station` table. The scraper will automatically initialize this table from its configuration.

You can use a tool like `psql` to run these files. For example:

```bash
psql -U <username> -d <database_name> -f common/timescaledb_schema.sql
psql -U <username> -d <database_name> -f common/initial_data.sql
```

## Deployment

Both sub-projects deploy to [Fly.io](https://fly.io) (apps `windburglr` and `windburglr-scraper`) with
their `fly-deploy.sh`, run from a clean checkout. The script tags the build with the commit SHA as the
Sentry release; set `ALLOW_DIRTY=1` to deploy uncommitted changes anyway. Extra arguments go to
`flyctl deploy`.

-   **webapp**: if `webapp/.env.sentry-build-plugin` (`SENTRY_AUTH_TOKEN=...`) exists, the build uploads
    source maps to Sentry. The maps are not served.
-   **scraper**: station config is kept out of the repository and the image. The scraper reads it from
    the `SCRAPER_CONFIG` secret (base64-encoded TOML). When `scraper/windburglr.prod.toml` exists, the
    deploy script stages it as that secret first. Use `SCRAPER_CONFIG_FILE` to name a different file.
    Locally, the scraper reads `--config-file` (default `windburglr.toml`) when `SCRAPER_CONFIG` is unset.

Runtime settings such as `DATABASE_URL` and `SENTRY_DSN` are Fly secrets (`flyctl secrets list`).
